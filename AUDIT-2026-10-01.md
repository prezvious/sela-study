# sela. audit and fix report — 1 October 2026

The existing application at `C:\Users\camar\Documents\Coding\sela-study` was audited and fixed in place. Thirteen new defects were reproduced against current source: twelve affect a supported UI/data workflow, sometimes under rare historical conditions, and one is an accepted timestamp boundary defect with limited normal UI impact. Historical reports were read as context and their findings rechecked; their old findings were not counted again.

Five distinct subagents covered timer/data integrity, storage/concurrency, cloud/SQL/server boundaries, new stress-test implementation, and independent final localisation/UI review. ## Confirmed findings

### A001 — Stale recovery can overwrite repaired records (P1)

**Trigger:** Tab A opens recovery for corrupt persisted JSON. Before A confirms, tab B repairs the same store and saves genuine version-2 subjects/tasks or starts a timer. Its storage event can be delayed, or delivered before confirmation.

**Expected / actual:** A should refuse a stale recovery without changing the repaired records. Previously it replaced them with an empty state, bypassed the current active-timer guard, and downloaded only A's original corrupt bytes rather than B's records.

**Cause:** `replaceData()` selected A's stale state whenever recovery was requested, without rereading the persisted raw snapshot. **Fix:** Capture the original raw snapshot when opening recovery, reread it under the study lock, and reject a mismatch before backup or replacement. The same check protects replacement while unreadable data is present. An unchanged corrupt snapshot remains recoverable.

**Verification:** `audit-regressions.test.mjs` checks repaired tasks and active timers with both delayed and delivered storage events. The exact repaired bytes remain unchanged; no misleading backup is generated. The unchanged-corrupt recovery path still downloads the original bytes and succeeds.

### A002 — Delayed import responses replace newer dialogs/selections (P2)

**Trigger:** A JSON file's `text()` promise is pending while the user navigates or opens a task draft; alternatively choose files A then B and let B resolve first.

**Expected / actual:** Preserve the newer view/draft or most recent selection. Previously a late response opened its import confirmation unconditionally, replacing the task dialog or file B's confirmation with older file A.

**Cause / fix:** The import handler lacked the UI lifetime guard used by cloud reads. It now records an import sequence and UI epoch and discards a stale response before parsing/opening its confirmation.

**Verification:** Actual handler regressions cover navigation, new task dialogs, reverse read order and successful confirmation of the newest file. Existing large-import, quota and recovery checks still pass.

### A003 — Midnight daylight-saving changes overlap daily totals (P1)

**Trigger:** In `America/Santiago`, a valid session runs from `2026-09-06T23:30:00-03:00` to `2026-09-07T00:30:00-03:00`. September 6's midnight is skipped by a clock-offset change.

**Expected / actual:** Thirty minutes on each date, sixty minutes combined. Previously separate daily totals were sixty and thirty minutes: their sum was ninety minutes, although the combined interval was sixty minutes. History's clipping boundary used the same faulty arithmetic.

**Cause:** A nonexistent midnight normalized to 01:00, and `setDate()` preserved that hour into the following date. **Fix:** Calendar arithmetic builds the target civil date and resets its clock to that date's local start. `sessionParts()` advances with that boundary. Backwards iteration also progresses across Apia's skipped civil date.

**Verification:** Targeted daily/history assertions pass. The new seven-zone stress oracle independently counts UTC-minute slices through explicit-zone Intl formatting; daily totals conserve duration through midnight, 23/25-hour days, half-hour transitions and the Apia skipped date.

### A004 — Timers older than 366 days cannot finish or export (P2)

**Trigger:** An otherwise valid timer remains running for 367 days, naturally or following a forward system-clock change.

**Expected / actual:** Finish/export should preserve the elapsed interval. Previously the active timer validated, but finishing or exporting produced a format error because its saved interval exceeded a separate 366-day cap. It remained running.

**Cause / fix:** Saved and active intervals had inconsistent rules. The arbitrary saved-duration restriction was removed; finite safe timestamps, exact durations, record limits, subject/run integrity and nonoverlap checks remain. A long uninterrupted focus remains one record, with no schema extension or artificial pause.

**Verification:** Finish and backup round trips preserve 366 days minus one millisecond, exactly 366 days, plus one millisecond and 367 days. Backup leaves the source timer unchanged; aggregate total and longest-focus values are preserved.

### A005 — Accepted extended-year sessions produce NaN parts (P3, boundary)

**Trigger:** A valid one-hour interval on `+010000-01-02`, or at the maximum supported JavaScript timestamp, is passed to `sessionParts()`.

**Expected / actual:** Finite parts summing to one hour. Previously an unsigned extended-year date string failed to parse, producing a NaN part end/duration.

**Cause / fix:** Splitting round-tripped a numeric timestamp through a four-digit date-string assumption. It now computes the next boundary directly from the numeric Date; at Date's upper endpoint it clips to the finite interval end.

**Verification / impact:** Both boundaries have exact finite conservation tests. Normal current-date UI ranges already clip far-future imported records out; this is an input/helper boundary fix, not evidence of ordinary users seeing NaN totals.

### A006 — Account changes during Auth/backup reads return stale account data (P2)

**Trigger:** A request captures account A, then Auth switches to B or signs out while `getUser()` or the backup query is pending. An A→B→A sequence also invalidates the original confirmation.

**Expected / actual:** Reject the stale response. Previously a query could return A's backup and A's context while the current account was B; the connection/configuration check alone did not detect it.

**Cause / fix:** Cloud guards tracked project configuration but not account identity lifetime. Client auth subscriptions now track identity revisions and connection generations; checks after asynchronous boundaries also inspect the SDK's saved user identity to detect changes before a storage event. Obsolete subscriptions are removed. Same-account token refresh preserves valid operations, following the documented [Supabase Auth event API](https://supabase.com/docs/reference/javascript/auth-onauthstatechange).

**Verification:** `cloud-audit.test.mjs` and seeded cloud schedules exercise delayed Auth/query responses, sign-out, A→B→A, changes before storage events, key/project invalidation, refresh and listener cleanup. Context metadata contains no credentials. These are controlled SDK tests.

### A007 — A queued cloud restore commits after account/project changes (P2)

**Trigger:** Restore confirmation passes its async context check as A, then waits for the study lock. Account or project changes before the lock is granted.

**Expected / actual:** Leave local records untouched and reject the outdated restore. Previously the local write succeeded with A's backup under the new context. A recovery backup was created, but the context check no longer described the operation being committed.

**Cause / fix:** The check preceded another asynchronous wait. `replaceData()` now accepts a synchronous guard, executed inside the acquired lock immediately before backup and persistence. Cloud restore uses the identity/configuration guard there. The callback remains synchronous for the IndexedDB mutex fallback.

**Verification:** Actual restore handlers reject account/project changes and auth-storage changes while queued, preserving local records, leaving the confirmation open and generating no replacement backup. A same-account refresh permits the intended restore.

### A008 — Historical calendars are labelled “this week/month” (P2)

**Trigger:** Navigate to an earlier or later week/month in Calendar, in any of the six languages.

**Expected / actual:** The footer should identify the selected period. Its total was correct, but all six catalogues described it as the current week/month.

**Cause / fix:** Fixed footer wording assumed today's period. Twelve catalogue values now refer to the selected week/month, preserving the same keys and interpolation parameters.

**Verification:** Actual historical calendar renders in all six languages show the revised wording and expected duration. Catalogue completeness/placeholder checks retain 371 keys per locale, 2,226 entries total. Static bundled translation and user-entered text are preserved.

### A009 — Date-picker grid lacks required accessibility structure (P2)

**Trigger:** Open the date picker in any locale.

**Expected / actual:** A named grid owns rows, which own headers/cells. Previously 7 headers and 42 gridcells were direct grid children, with zero rows and no grid name. This violates the [WAI-ARIA grid requirements](https://www.w3.org/TR/wai-aria-1.2/#grid).

**Cause / fix:** Calendar layout used flat markup. The picker now has a localised month/year name, one header row and six date rows. App CSS retains the seven-column appearance; copied vendor files are unchanged.

**Verification:** Actual rendering-function tests check all six languages. Native browser accessibility trees expose a named month table with seven rows. At 320 pixels every locale fits without horizontal page overflow; Russian also fits at 1440×960. ArrowRight then Enter selects the next canonical date and returns focus to the input. Native screen-reader speech has not been tested.

### A010 — Subject lifetime totals omit valid records before 2000 (P2)

**Trigger:** Import a valid one-hour study record from 1999, or an epoch-zero record whose local date can be in 1969.

**Expected / actual:** The subject should show one hour of total study time. Previously it showed zero while correctly counting one record, in all six languages.

**Cause / fix:** `subjectsView()` used a hard-coded `2000-01-01` aggregate lower bound. It now sums stored and active intervals directly into a prototype-safe subject dictionary, with no arbitrary lifetime cutoff or dependence on the local date of epoch zero.

**Verification:** UI regressions check exact one-hour totals for 1999 and epoch-zero records in UTC, Los Angeles and Singapore, in all six languages, including a prototype-like subject identifier. Existing stored records are not rewritten.

### A011 — A skipped civil date shifts or duplicates calendar cells (P2, historical timezone condition)

**Trigger:** Open December 2011 in `Pacific/Apia`, where December 30 never occurred. A task dated December 31 is valid and can open this picker.

**Expected / actual:** December 31 stays in Saturday's column and appears once. Previously the picker put it under Friday and shifted subsequent dates; the main month heatmap duplicated December 31. These failures affected all six locales, with the expected different US week start.

**Cause / fix:** Date arithmetic correctly skipped the nonexistent day in chronological iteration, but a civil calendar grid still needs its slot. A shared calendar-slot helper now returns a disabled/empty placeholder for nonexistent local dates. Date-picker, month, week and contribution grids retain their columns without making an impossible date selectable. Timer/statistical splitting continues to skip nonexistent time normally.

**Verification:** All six date-picker grids are checked against independently enumerated Gregorian civil dates in UTC: 42 slots, one disabled missing-date placeholder and exact positions for every valid date. Month/week/contribution grids contain December 31 once and no selectable December 30. The timezone stress oracle still conserves elapsed time across the skipped date.

### A012 — Streaks omit pre-2000 and epoch activity (P2, historical clock condition)

**Trigger:** Evaluate the current streak on September 23, 1999 with a valid one-hour record that day, or on January 1, 2000 after studying on December 30, December 31 and January 1. Epoch-zero activity can also occur on local December 31, 1969 in western timezones.

**Expected / actual:** The examples should report one day and three days respectively. Previously they returned zero and one because activity before 2000 was excluded. The UI summary used this helper and displayed the same incorrect counts.

**Cause / fix:** `streak()` had a hard-coded `2000-01-01` aggregate lower bound. It now starts on the local calendar date of timestamp zero, the earliest permitted session start. Using the local date also retains epoch activity in negative-offset zones. Current-day and yesterday-based streak rules remain intact.

**Verification:** Explicit independent day-count fixtures cover today, yesterday, consecutive days, an interrupted gap, old-only activity, empty records, the year-2000 transition, epoch zero and current-day records in UTC, Los Angeles and Singapore. Actual summary renders agree with the historical counts.

### A013 — Early-year month views and navigation jump 1,900 years (P3, date boundary)

**Trigger:** Display October in year 99, or navigate across the year-99/100 boundary. Four-digit task dates in years 1–99 are accepted by the application; a historical clock or repeated calendar navigation can select those months.

**Expected / actual:** Year 99 should remain year 99. Previously the month heading showed October 1999 and its first cell was `1999-09-27`, while the selected date was in October 99. Statistics ranges and month navigation used the same construction.

**Cause / fix:** JavaScript's multi-argument Date constructor applies a 1900 offset to years 0–99. A local month-boundary helper now uses `setFullYear()`, preserving the actual year. Calendar month bounds, statistics ranges, both navigation paths and live calendar footer updates use it.

**Verification:** Ninety locale/timezone/date fixtures independently enumerate expected civil dates in UTC. They check full month grids, exact statistics days, previous/next navigation, live footer stability and unchanged persisted task bytes. Fixtures cover years 1, 42, 99, 100 and 2026, all six languages, and UTC/Los Angeles/Singapore. `early-year-before.json` records the original year-99→1999 failure.

## Limits and findings not counted as bugs

- The 24 server boundary fixtures produced expected 200/403/404 responses and zero reads outside the dist root. This does not prove every filesystem/deployment configuration is safe.
- No new SQL flaw was reproduced through the supported RPC path. Authenticated users retain direct write access to their own rows; manual writes can bypass RPC revision/version checks. SQL checks the version marker, while full study-schema validation occurs in the app. These are existing boundaries, not a reproduced cross-account-access bug.
- Supabase authentication, email redirects, live RLS/RPC behaviour, SDK delivery ordering, service payload limits and production hosting remain unverified. Mocks and local PostgreSQL fixtures do not establish live behaviour.
- Most concurrency/storage stress uses controlled DOM, lock and storage doubles. The prior native IndexedDB check remains historical evidence; this pass did not repeat every browser's fallback, quota or multi-tab implementation.
- The chart's `role="img"` around interactive bars was reviewed as an accessibility concern, but native focusable-descendant exceptions prevent a confident failure claim without screen-reader testing. It remains unconfirmed. Larger date-picker touch targets and independent professional translation review are optional improvements.
- Passing these checks does not prove the application is bug-free.
